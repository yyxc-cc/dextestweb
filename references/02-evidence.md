# 02 · 取证与验证：把"我觉得有问题"变成"这就是问题"

## 一条铁律

**每个结论两种证据，缺一条只能写"疑似"。**

| 结论类型 | 证据 A | 证据 B |
|---|---|---|
| 页面显示错 | 截图（含地址栏、分页文案） | 接口返回 / 数据库字段 |
| 数据被改坏 | 数值变化序列（1→9→13…） | 列表回读 / 接口 |
| 搜索查不到 | 结果 0 条截图 | 地址栏参数 / 请求体 |
| 资源缺失 | 屏幕上的乱码/空白 | 网络记录里的 404 URL |
| 慢 | 秒表截图/日志时间戳 | 视频时间点 |

## 三查法：页面 → 接口 → 库

1. **页面**：用户看到的（截图 + 地址栏）
2. **接口**：系统实际拿到的（`page.on('response')` 抓返回，或直接 `fetch` 复打）
3. **库**：数据实际变成什么（有权限/有查询入口时）

大多数"看起来坏了"的问题，在第 2 步就能定性：

- 接口 200 且数据正确 → 前端渲染/映射问题
- 接口 total 有值、页面写 0 → 前端没接分页
- 接口 4xx/5xx → 后端或网关
- 接口参数不对（`0=D&1=C&2=1`）→ 前端拼接 bug

## 五个高频可疑点 + 验证脚本

### 1. 分页总数恒为 0

```js
const s = await page.evaluate(() => {
  const main = document.querySelector('.app-main');
  const vis = (e) => e.getBoundingClientRect().width > 0;
  return {
    rows: main.querySelectorAll('.el-table__body tbody tr').length,
    pag: [...main.querySelectorAll('.el-pagination')].filter(vis)
      .map((p) => (p.innerText.replace(/\s+/g, ' ').match(/共\s*\d+\s*条/) || [])[0]).filter(Boolean)
  };
});
// rows > 0 && pag 是"共 0 条" → 记录；再补一条接口 total 作为对照
```

### 2. 搜索参数被拆成单字符

看地址栏：`#/searchResult?0=D&1=C&2=1`。正常应该是 `keyword=DC1`。
补证：在 Network 里看请求体/query，确认后端拿到的是三个独立字符。

### 3. 保存失败但不回滚（最严重的一类）

现象：提示"超量/校验失败"，列表里的数量却变了。

验证：

1. 记下操作前的值（截图或接口）
2. 触发一次失败保存
3. 刷新列表，记下新值
4. 再触发一次，看是否**等量累加**（1→9→13…说明每次失败都 +N）
5. 查明细表（如编码表）确认"主表变了、明细没写"

结论措辞：**"校验失败时未回滚已变更的数量字段，失败 N 次累加 N×Δ"**，比"数据不一致"有力得多。

### 4. 列表"空白"

按顺序排除，**每一步都要留记录**：

1. loading 遮罩 / 转圈还在？→ 继续等
2. 分页有总数但 0 行？→ 渲染问题
3. 换筛选（默认筛选常常是空的）→ 逐个筛选跑一遍
4. 刷新重进 → 排除路由缓存
5. 接口有数据、页面仍空 → 前端问题，记下筛选条件与接口返回

### 5. 慢 / 卡 / 超时

- 用 `performance.now()` 或日志时间戳量，别估
- 至少测两轮（例：4.4s / 5.0s），报告写区间不写单点
- 归到"性能/交互"，不要归到"功能缺失"

## 复现步骤怎么写才算合格

合格标准：**另一个人不看你的说明，只按步骤操作，能得到同样结果。**

```
1. 生产订单管理 → 选 PO_202610120176（轮毂，计划 4 件，当前已投 1）
2. 点「物料建码」→ 添加 → 勾选该订单 → 确定（弹窗约 15 秒打开）
3. 前缀填 TSV，起始号 1，数量 4 → 点上方「确定」生成 4 个编码
4. 点下方「确定」保存 → 顶部红字提示「剩余可投数量为 3.0，请检查！」
5. 关闭弹窗，刷新列表 → 该订单已投变成 5（每次重复步骤 1-4，+4）
```

带时间、带数值、带按钮原文。不要写"操作一下建码功能"。

## 级别怎么定

| 级别 | 判据 | 例子 |
|---|---|---|
| P0 | 数据错了/丢了/改不回来；账实不符 | 保存失败但已投数量累加；库存被扣两次 |
| P1 | 主流程走不通，或核心查询失效 | 搜索永远 0 条；提交后单据不生成 |
| P2 | 显示错误、统计不对、明显体验缺陷 | 分页恒为 0；列表字段错位；切换无 loading |
| P3 | 文案、样式、图标 | 错别字；图标 404；对齐问题 |

级别按**后果**定，不按修复难度定。

## 措辞

- ✅ "计划 4 件的订单，已投数量被 7 次失败保存累加到 33；编码表 0 条新增。"
- ❌ "数据一致性存在问题。"
- ✅ "任意关键字搜索均返回 0 条，地址栏参数被拆成 `0=D&1=C&2=1`。"
- ❌ "搜索功能不可用。"

## 推翻自己的结论

测早期最容易犯的错：把"还没加载完"当"没做"。一旦后续验证推翻了早期结论：

1. **不要偷偷改**，在报告里加一张"更正表"：原说法 / 实际情况 / 为什么误判
2. 更正本身是专业度的体现，客户会更信你后面的结论
3. 同时把"为什么会误判"写进流程（等待条件、双证据），避免下次再犯
